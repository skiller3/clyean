# Architecture

Clyean is two programs and a contract between them.  On the host runs `clyean`, a Rust program that owns the project's scaffold, the Podman sandbox, and the orchestration of agents.  Inside the sandbox runs the contained harness, Clyean's fork of Oh-My-Pi, one process per agent.  The contract is the [sandbox layout](../reference/sandbox-contract.md) every agent sees and the [socket protocol](../reference/orchestrator-protocol.md) the User Assistant uses to reach the host.

## The host program

`clyean` is a Cargo workspace whose crates separate concerns and depend on each other in one direction only: project state (`clyean-project`), Git (`clyean-git`), the agent roster and profile projection (`clyean-agents`), PlantUML (`clyean-plantuml`), the bridge between a User Assistant container and its `clyean` process (`clyean-bridge`, which also builds the static `clyean-bridge` executable that runs inside the container), the Podman sandbox (`clyean-sandbox`), the harness RPC client (`clyean-harness`), orchestration (`clyean-orchestrator`), and the command line (`clyean`).  Nothing in the host program talks to a model.  Everything that requires judgment is delegated to an agent; everything that must be exact (layout, locking, commits, rendering, workflow order, bounded retries) is deterministic Rust.

## One root filesystem, one container per agent process

All agents of a project share one root filesystem, a directory that Clyean keeps beside Podman's own data on the Podman host (inside the Podman machine on native Windows and macOS) and names by a random identifier recorded in the project's local-only `.clyean/sandbox.local.json`.  Clyean populates it by streaming an export of the configured image into a helper container that extracts it, and then provisions it.  Every agent container is started with `podman run --init --rootfs <that directory>`, so PID 1 is Podman's init and the harness process is its only child.  A directory rather than an image layer has three consequences that the design wants: packages one agent installs are there for the next; the whole sandbox is a plain directory Clyean can inspect, rebuild, or delete; and nothing an agent does can escape it, because the only writable path outside the root is the workspace mount and the only connections out are the User Assistant's bridge channels.  Keeping it outside the project keeps it off the workspace mount and off filesystems, such as a Windows drive, that cannot hold it, and keeps it beyond the reach of Podman's prune commands.

The workspace is mounted read-write at `/home/<user>/workspace/<name>`; additional host paths are mounted read-only under `/mnt`.  Under rootless Podman the container's root is your own user, which keeps ownership of every file an agent writes sane.

Everything Clyean does to a root filesystem goes through one interface with two implementations: direct file access when Podman runs on the same kernel (Linux, and Linux on WSL), and short-lived containers on the root filesystem when it runs in a Podman machine, which Podman's remote client reaches.  A launch batches its writes (every agent's profile and the marker's record of this use) into one archive, so a Podman machine costs one container start for them.

Each agent runs under its own harness profile (`OMP_PROFILE=<agent-id>`), which is how models, credentials, MCP servers, and sessions stay separate per agent without changing the harness's configuration model.  Clyean projects the tracked files under `.clyean/agents` into those profiles before every start, layering the project's settings overlay over each profile's own persisted state through the harness's `--config` flag.  Each agent's containers expose only that agent's profile, and with it only that agent's login store.  The user signs in through the User Assistant, whose store holds every sign-in.  When a sub-agent starts, the orchestrator works out from the agent's configuration which providers and MCP servers it needs, asks the User Assistant over its lease connection for copies of those credentials, without refresh tokens, and delivers them through a file in the agent's profile, which the agent's credentials extension imports before the harness decides which models are available.  When a copy nears expiry, the sub-agent asks the orchestrator for a fresh one through an extension UI request, and the User Assistant refreshes the sign-in itself.  Host variables are selected the same way: the User Assistant receives the provider variables it may need, and each sub-agent only those of its own providers.

## The User Assistant and the orchestrator

Every `clyean` invocation starts one User Assistant, an interactive harness session in a container of its own that the invocation runs in the foreground and that ends with it.  A second invocation in the same project gets a second container and its own session on the same root filesystem.  Nothing attaches to a running User Assistant, so the pairing between a process, its container, and its agent never breaks.

The User Assistant cannot start containers itself (the Podman socket is deliberately not mounted), so it delegates through tools provided by a Clyean-managed extension.  Those tools speak newline-delimited JSON over the Unix socket `/run/clyean/orchestrator.sock` inside the container.  No host socket is mounted: the socket belongs to the bridge, which `clyean` starts in the container with `podman exec` once the container runs.  The bridge turns each connection into a stream multiplexed over the exec session's standard input and output, and `clyean` connects the stream to the orchestrator, or, for the Herdr socket the bridge also serves inside Herdr, to the host's Herdr socket.  One request per connection; the host answers immediately and then streams progress until the work completes, fails, or needs information from the user.

The bridge also ties the User Assistant's life to its `clyean` process.  The container's command waits until the bridge is serving before it starts the harness, and the extension holds a lease, one orchestrator connection kept open for the harness's whole life.  When the `clyean` process ends for any reason, the exec session's input closes, the bridge exits, the lease ends, and the extension shuts the harness down, after which Podman removes the container.  A harness too stuck to act on its lease leaves a container with no bridge behind, which `clyean sandbox prune` removes.

The orchestrator runs inside the `clyean` process that started the User Assistant.  It takes the project lock, opens one harness session per sub-agent per unit of work (each in its own container, driven over the harness's RPC mode), sends one instruction per workflow step, reads the verdict from the last fenced `json` block of the reply, commits after each step, and relays the sub-agents' output back to the User Assistant.  When a step needs an answer from you, the orchestrator suspends the workflow with the sub-agent sessions still alive, the User Assistant asks you, and the answer flows back through the same socket.

## Sessions and context

The Clyean session is the User Assistant's harness session, which is why `--continue` and `--resume` work as they do in the harness.  Every other agent gets a fresh session for each unit of work and keeps it for the whole unit, including across information requests.  Resetting sub-agent context for every prompt is a deliberate defense against technical debt: an agent that carries the accumulated context of earlier changes drifts toward the shortcuts it took before, while an agent that starts from the specification, the architecture, and the plan reasons from the recorded state of the project.

## Durable execution

Every unit of work has a journal that records its phase, the questions and answers so far, the sub-agent session files, and the commits made after each step.  The journal is saved on every transition and, for plans, committed to Git with the plan.  A workflow that is interrupted resumes from its recorded phase, re-opening the recorded sessions, and a workflow that is waiting for information replays its questions.  Git is the record of the work itself: each step's output is a commit authored by the responsible agent with a `Clyean-Agent:` trailer.
